# 【Day 08】売上登録APIを作る：明細と金額計算を正しく扱う

シリーズ：**Next.js・Python・AWSで作る売上管理システム**

公開予定：2026年12月8日（日本時間）。開発・レビュー・Qiita公開は分けて管理しています。

## はじめに

[Day 7](https://github.com/hirolisberger/sales-manager-dashboard/blob/day07/qiita/day07-product-master-api.md)で作成した商品APIを使い、売上を登録する`POST /sales`を実装します。

今回は、税込単価と数量から金額を計算し、取引時の商品情報を残します。売上本体だけ保存されて履歴が欠ける状態を避けるため、日付別のデータと再送用記録も同時に保存します。

売上の一覧・詳細取得はDay 9、訂正・取消はDay 10の予定です。今回の確認にはHTTPの登録応答と、ローカルDynamoDBの読み取りを使います。画面や認証はまだ追加していません。

## この記事の到達点と前提

- 税込整数円×整数数量で明細金額・合計を確定する
- 日本時間の本日以前の計上日だけ受け付ける
- 取引時の商品コード・名称と実際の単価を残す
- 売上・日付別データ・履歴・再送用記録を一括保存する
- 同じ要求の再送で売上が増えないことを確認する

確認日は2026年11月2日。macOS ARM64、Python 3.14.9、uv 0.13.6、MiniStack 1.5.33とDay 7までの固定依存を使用しました。依存やロックファイルは更新していません。日本時間の判定にはOSのIANAタイムゾーンデータを使います。

リポジトリは [sales-manager-dashboard](https://github.com/hirolisberger/sales-manager-dashboard) です。Day 8はレビュー待ちで、完成版の[`day08`タグ](https://github.com/hirolisberger/sales-manager-dashboard/tree/day08)は承認・mainマージ後に作成します。以下のday08文書リンクもタグ作成後に参照可能になります。

## 1. 金額の入力と計算を分ける

クライアントから受け付ける項目は、計上日と明細だけです。

```json
{
  "sale_date": "2026-11-02",
  "lines": [
    {"product_id": "00000000-0000-4000-8000-000000000001", "unit_price_yen": 550, "quantity": 2}
  ]
}
```

このJSONは形式の例で、商品IDは架空です。動作確認では実際に登録した商品のIDを使い、計上日も実行時点の日本時間に合わせます。

| 入力 | ルール |
| --- | --- |
| 税込単価 | 整数0〜9,999,999円 |
| 数量 | 整数1〜9,999 |
| 明細数 | 1〜50件 |
| 計上日 | 実在するYYYY-MM-DD、日本時間の本日以前 |

`550.0`、`"550"`、`true`を整数へ変換せず、422で拒否します。未知の項目も受け付けません。合計、商品名、操作者、状態、版、IDはサーバー側で決める値です。入力検証には、Day 5からの厳格な共通モデルとフィールド検証を使います。[Pydantic公式資料](https://docs.pydantic.dev/latest/concepts/validators/)

```text
明細金額 = 取引時の税込単価 × 数量
売上合計 = 明細金額の合計
```

550円×2個なら1,100円です。売上合計は9,999,999,999円以下に制限し、超過は422 AMOUNT_LIMIT_EXCEEDEDにします。Pythonの整数で計算し、浮動小数点を使いません。

Day 1で税込整数円を採用したため、税額の加算・逆算や端数処理はありません。0円の商品明細は許可しますが、数量0や負の金額・数量は受け付けません。同じ商品を複数明細に指定することは可能で、明細ごとに実売単価を残せます。

## 2. マスタの標準価格と、実際の販売価格を区別する

登録された有効商品を現在の店舗内から読み取ります。売上明細には次の値を保存します。

- サーバーが発行した明細UUIDと、入力順の明細番号
- 商品IDと、その時点の商品コード・名称
- 入力された実売単価・数量・計算済みの明細金額

標準価格600円の商品を、550円で2個販売したなら1,100円です。標準価格をそのまま売上の単価に上書きしません。過去日の売上も、実際に取引した単価で登録できます。

商品名は登録時点のマスタから保存します。後からマスタを改名・値上げ・無効化しても、登録済み売上の明細は変わりません。過去日の商品名を自動復元する価格・名称履歴の機能はありません。

## 3. 計上日と操作時刻を分ける

`sale_date`は日本時間の取引日です。サーバーのタイムゾーン付き時計を`Asia/Tokyo`へ変換し、本日より未来なら422 FUTURE_SALE_DATEで拒否します。作成・更新・履歴の操作日時は、同じ時計からUTCで保存します。[Python公式資料](https://docs.python.org/3.14/library/zoneinfo.html)

テストでは、2026年11月1日14:59:59 UTCと15:00:00 UTCを固定時計として使いました。日本時間では11月1日23:59:59と11月2日0:00:00です。計上日11月2日が、前者では拒否され、後者では登録できることを確認しました。PCやOSの時計は変更していません。

## 4. 4つの保存先と商品確認を一つにまとめる

Day 4の保存設計とDay 6のリポジトリを使い、次の項目を同時に確定します。

| 項目 | 保存する内容 |
| --- | --- |
| 売上本体 | 明細配列・合計・計上日・confirmed・版1 |
| 日付別データ | 本体と同じ内容。将来の検索・集計に使う |
| 登録履歴 | created、操作者、日時、before=null、after=売上全体 |
| 再送用記録 | 要求内容のハッシュと最初の201応答 |

さらに、使った商品ごとに「読み取った版から変わっていない」「有効なまま」を確認するConditionCheckを追加します。TransactWriteItemsは、複数の書込・条件確認をまとめて成功または失敗させるAPIです。同じ項目へのアクションを重複できないため、同じ商品を複数明細で使っても商品確認は1回にまとめます。[AWS公式資料](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html)

商品が50種類なら4＋50＝54アクションです。MiniStackでは100文字の補助平面Unicode名称を持つ商品50件・50明細でも登録を確認しました。Day 6の項目・要求サイズの保守的なガードも使います。実AWSの上限試験や負荷性能を確認した結果ではありません。

読取後に商品が改名されたら409 PRODUCT_CHANGED、無効化されたら409 PRODUCT_INACTIVEとし、売上4項目は保存しません。先に読んだ商品情報で勝手に確定したり、途中の履歴だけが残ったりしないことを検証します。

## 5. 同じ要求を再送しても増やさない

登録には、Day 7と同じ`Idempotency-Key`ヘッダーを必須にします。

```text
同じキー・同じ本文 → 最初の201応答を再送
同じキー・異なる本文 → 409 IDEMPOTENCY_CONFLICT
別の売上を登録 → 新しいキーを使用
```

再送では元の売上ID・明細ID・日時・ETagも返し、`Idempotency-Replayed: true`を付けます。商品の改名・無効化やAPIアプリの再作成後も、保存された記録から同じ応答を返します。

キーは店舗・操作者内で商品APIとも共有します。商品登録と売上登録にはそれぞれ新しいUUIDを使います。キーだけではなく、POST・パス・検証後の本文も照合します。同時処理がまだ確定していない場合は503の可能性があり、Retry-Afterを待って同じ要求を再送します。

## 6. ローカルで登録・再送・保存内容を確認する

すべて`sales-manager-dashboard/`で実行します。[DAY8_COMMANDS.md](https://github.com/hirolisberger/sales-manager-dashboard/blob/day08/docs/DAY8_COMMANDS.md)の手順1〜4で、依存・MiniStack・テーブル・APIを準備し、確認用の商品と売上本文を作成してください。商品コードと要求キーを毎回生成するので、既存商品を変更しません。

用意した本文を送信するコマンドは次のとおりです。

```sh
curl -sS -D .cache/day08-created-headers.txt \
  -o .cache/day08-created.json -w '%{http_code}\n' \
  -X POST http://127.0.0.1:8000/sales \
  -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $(cat .cache/day08-sale-key.txt)" \
  --data-binary @.cache/day08-sale-body.json
cat .cache/day08-created-headers.txt
python3 -m json.tool .cache/day08-created.json
```

201・ETag: "v1"・合計1,100円が目印です。同じキーと本文で再送すると201のまま同じ内容を返し、再送ヘッダーがtrueになります。キーを生成するPythonまで実行し直すと別の要求になるため、再送の確認ではcurlだけを繰り返します。

手順書にはローカルSDKで本体・日付別データ・登録履歴を読むコマンドも記載しました。実機確認では3つの一致判定がtrueになりました。売上GET APIはまだ用意していないため、今回のブラウザー確認用URLはありません。
