# 全25日の開発・記事計画

## 進め方と前提

- この表は計画であり、実施・承認・公開の実績ではない。状態は [PROGRESS.md](PROGRESS.md) で管理する。
- 各記事のタイトル・概要案は [ARTICLE_PLAN.md](ARTICLE_PLAN.md) にまとめる。この表では開発テーマ・成果物・確認項目を管理する。
- 業務前提は [README.md](../README.md) を参照する。小規模店舗・管理者のみ・税込を基本とし、日別・月別の集計切り替えと過去の売上参照を対象とする。
- 現在は初期設定のみ。ユーザーの開始指示があるまでDay 1には着手しない。
- 開発は毎日行う必要はなく、ユーザーの都合に合わせて進める。1回の作業は原則一つのDayを対象とし、実装・設定・設計などの成果物とMarkdown記事をセットで作成する。
- 各Dayで検証を終えたらレビュー待ちにして停止する。対象Dayへの明示的な「レビューOK」とmainへのマージを経て、次のDayへ進む。
- 次のDayへの着手には実装完了、必要な動作確認、記事Markdownの完成、レビュー承認が必要。Qiitaへの投稿・予約登録・公開完了は条件に含めない。修正指示はコードと記事の両方に反映する。
- 開発日と公開日は別に扱う。公開予定日は2026年12月1日〜25日に固定し、Day番号と日付を対応させる。日本時間（Asia/Tokyo）で管理し、公開時刻は未設定。予定日前に全体公開しない。
- AWSサービス、APIフレームワーク、IaCは候補。採用するDayに公式仕様とLocalStackの対応範囲を確認し、決定事項を記録する。
- 公開予定に合わせるために検証やレビューを省略しない。開発範囲・開発日程の変更はユーザーと調整し、公開が遅れても固定の公開予定日は書き換えず実績と分けて記録する。

## 計画変更と実環境の扱い

機能や構成を見直す場合は、影響するDayと記事の変更点を示し、進捗にも記録する。完了済み・承認済みの履歴は消さない。

AWS実環境での作業には、対象アカウント・リージョン・構成差分・費用・後片付けを示し、許可を確認する。許可や環境が用意できない場合、IaCの作成・検証など独立して進められる範囲を実施し、実環境確認を未完了として残す。未実施のデプロイや復旧検証を記事で成功したように扱わない。

Day 25の完成は、記事の投稿・更新・予約登録・全体公開の許可にはならない。記事は下書きから作成し、Qiita操作は明示的に許可された範囲でのみ行う。予約登録にはQiita公式のAdvent Calendar予約投稿機能を優先し、対象日と登録結果を記録する。登録失敗・確認不能の場合は未登録として報告し、公開予定日と実績を分けて管理する。
