- 記事作成前の既存6コミット・26ファイル版について、AWSアクセスキー、GitHubトークン、秘密鍵、個人を含む絶対パスの既知パターンを検査し、該当なし。ただしパターン検査だけで公開の安全性を保証するものではない。

## 状態の定義

| 管理項目 | 使用する状態 | 更新する条件 |
| --- | --- | --- |
| 開発 | 未着手 / 実装中 / 実装完了 | 設計・設定を含む当日の成果物と必要な動作確認を終えたら実装完了 |
| レビュー | 未着手 / レビュー待ち / 修正中 / 承認済み | 実装と記事が完成し、検証結果を提示したらレビュー待ち。ユーザーの明示的な「レビューOK」でのみ承認済み |
| 公開 | 未投稿 / 限定共有 / 予約登録済み / 公開済み | 明示的に許可された操作の成功を確認して更新。予約登録と実際の全体公開を区別する |

補助情報として、記事本文は「未着手 / 執筆中 / 完成」、mainマージは「未 / 済」で管理する。ローカルMarkdownの下書きは公開ステータス「未投稿」とし、Qiitaに非公開の下書きを保存した場合も、限定共有・予約登録を行うまでは「未投稿」のまま保存実績を別に記録する。

### 開発・レビューの更新ルール

- 開発は毎日行う必要はない。ユーザーの都合に合わせ、1回の作業は原則一つのDayを対象とする。
- 開発・レビュー・公開は独立して管理する。実装と記事が完成し、必要な動作確認を終えるまではレビュー待ちにしない。
- 次のDayへの着手には、現在のDayの実装完了、必要な動作確認の実施、記事Markdownの完成、ユーザーのレビュー承認がすべて必要。承認後はGit運用に従いmainへマージする。
- Qiitaへの投稿・予約登録・実際の公開完了は、次のDayへ進む条件に含めない。レビュー待ちの間は次のDayの開発を始めない。
- 修正指示はコードと記事の両方へ反映し、必要な動作確認をやり直す。未完成になった成果物の状態は戻し、承認後の実質的な変更は再レビューする。
- 必要な検証の未実施・失敗が残っている場合は、次のDayへ進めると判定しない。

### 投稿・予約・公開の更新ルール

- 公開予定日は固定する。Day 1は2026-12-01、Day 25は2026-12-25とし、早期の開発・承認を理由に予定日前に全体公開しない。
- レビュー承認だけを理由にQiitaへ投稿しない。下書き保存、限定共有投稿、更新、予約登録、全体公開はユーザーの明示的な許可を受けた範囲でのみ行う。
- 投稿・更新・公開の前に、記事の内容、対象URL、公開範囲を確認する。新規投稿でURLが未発行の場合はその旨を記録し、取得後に確認する。
- 全体公開の対象は、実装・記事が完成し、レビュー承認とmainへのマージが済んだDayに限る。
- 予約登録にはQiita公式のAdvent Calendar予約投稿機能を優先する。実行時に利用可否・操作仕様を確認し、対象日と登録結果を記録する。
- 「予約登録済み」は登録成功を確認した場合のみ使用する。失敗・確認不能の場合は予約結果を「未登録」とし、公開ステータスは直前に確認できた状態のまま、理由を記録して報告する。「未登録」は予約結果であり、公開ステータスには追加しない。
- 「公開済み」はQiitaで実際の全体公開を確認した場合のみ使用する。予約日になったことだけでは更新しない。
- Qiita記事URLは、限定共有や予約登録の段階でも取得後に記録する。URLの有無で公開範囲を判断しない。
- 公開予定日、開発完了日、レビュー承認日、実際の公開日時は別に記録する。時刻には `+09:00` を付ける。
- 公開が遅れても固定の予定日は書き換えず、遅延理由と対応を記録する。無断でまとめて公開しない。
