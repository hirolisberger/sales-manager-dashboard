## 1. 業務データ

| データ | 主な項目と不変条件 |
| --- | --- |
| 商品 | UUID、変更不可の商品コード、名称、税込標準単価、利用可否、版、UTC作成・更新日時 |
| 売上最新版 | UUID、JST計上日、confirmed/cancelled、版、JPY、明細配列、確定合計、UTC作成・更新日時 |
| 売上明細 | 明細UUID、並び順、商品UUID、取引時の商品コード・名称・税込単価、数量、明細金額 |
| 変更履歴 | 売上UUID、版、登録/訂正/取消、認証済み操作者、理由、UTC操作日時、変更前後の売上全体 |
| 冪等性記録 | 店舗・操作者・要求キー、要求のハッシュ、最初の成功時のHTTPステータス・本文・ETag |
| CSVジョブ（Day 17） | UUID、検索条件、状態、作成・完了日時、出力先・期限・失敗理由 |

価格は0〜9,999,999円、数量は1〜9,999、1売上は1〜50明細、売上合計は9,999,999,999円以下。小数、bool、文字列から整数への暗黙変換は認めない。商品コードは大文字英数字から始まる1〜32文字（以降は大文字英数字・`_`・`-`）、名称は空白だけを除く1〜100文字とする。商品コードは無効化後も予約を保持し、再利用・物理削除しない。

計上日はAPIの日本時間で本日以前。過去日訂正を認め、時刻のUTC保存とは分ける。訂正は同じ売上IDの版を増やし、取消は金額・明細を保持して集計から外す。取消の復活は設けない。

## 2. 単一テーブルのキー

初期構成は文字列の`PK`と`SK`を持つ1テーブル。GSI/LSIは作らない。`STORE#demo`は検証用の架空店舗で、本実装ではサーバー設定・認証情報から店舗を確定する。要求本文の店舗IDを信用しない。

| 項目 | PK | SK | 内容 |
| --- | --- | --- | --- |
| 商品 | `STORE#demo#PRODUCTS` | `PRODUCT#{商品UUID}` | 商品本体。一覧と詳細で同じ項目を読む |
| 商品コード予約 | `STORE#demo#PRODUCT_CODES` | `CODE#{商品コード}` | 対応する商品UUID |
| 売上最新版 | `STORE#demo#SALE#{売上UUID}` | `CURRENT` | 明細を含む売上全体 |
| 売上履歴 | 同じ売上PK | `REV#{10桁ゼロ埋め版}` | 変更前後・操作者・理由 |
| 日付別参照 | `STORE#demo#DAY#{YYYY-MM-DD}` | `SALE#{売上UUID}` | 最新版と同じ内容。取消済みも保持 |
| 冪等性記録 | `STORE#demo#REQUEST#{操作者ID}` | `KEY#{要求UUID}` | 最初の成功応答と要求ハッシュ |
| CSVジョブ（予定） | `STORE#demo#EXPORT#{ジョブUUID}` | `CURRENT` | 検索条件・状態・S3出力先など |

日付別参照は検索・集計・CSVのためのコピーで、非同期のGSIには依存しない。売上の最新版、日付別参照、履歴、冪等性記録を**同じトランザクション**で確定させる。

売上内に明細を配列として保存することで、明細50件を別々の項目へ保存する方式よりトランザクションの項目数を抑える。一方で、売上全体をコピーして読み書きする容量・費用が増える。無制限の明細・大量取引に適した設計とは扱わない。

## 3. アクセスパターン

| 操作 | 読み方・条件 |
| --- | --- |
| 商品詳細・コード確認 | 対応キーのGetItem。必要な箇所は強い整合性 |
| 商品一覧 | PRODUCTSパーティションをQuery、商品UUID昇順。利用可否のフィルターは読取後に適用 |
| 売上詳細 | 売上PK / CURRENTを強い整合性でGetItem |
| 履歴 | 売上PKと`REV#`前方一致でQuery、版の昇順 |
| 期間一覧 | 日付ごとのパーティションを強い整合性でQuery、計上日降順・同日売上UUID降順 |
| 日別・月別集計 | 同じ日付別参照からconfirmedの対象明細を選び、指定単位へ集計 |
| 商品別集計 | 同じ対象明細を商品UUIDでまとめる |
| CSV | 同じ対象明細を1明細1行にする。売上全体合計を各行に加算しない |

期間は開始・終了日を含む1〜366日。日別/月別の`group_by`は期間と独立させる。日別・月別の空バケットは0で補い、商品別は期間内の対象商品のみを返す。商品別の行は商品IDで識別し、名称表示は現在の商品マスタを参照する。CSVや売上詳細は取引時の名称を使う。

集計の`amount_yen`は対象明細金額、`quantity`は対象数量、`sale_count`は対象売上IDの重複を除いた件数。商品別のsale_countを足して全体の件数にしてはいけない。同じ売上にコーヒーと紅茶が含まれる場合がある。

### ページング

Queryの`Limit`はフィルター適用前の評価件数であり、1MiBの区切りもある。`Items=[]`でも`LastEvaluatedKey`があれば続ける。商品の絞り込みは埋め込んだ明細を調べるため、読み取り容量を節約する条件ではない。[AWS Query仕様](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_Query.html)

APIの`limit`は返す件数（1〜100、既定50）。内部では空ページを含めて読み進め、出力limitを超えて先読みした項目を飛ばさない位置にカーソルを置く。日付をまたぐ場合、次の日付と最後に消費したキーを保持する。カーソルは店舗・資源・期間・商品・状態・並び順・limitに結び付け、15分の期限とHMACで改ざんを拒否する方針。商品一覧に必要な部分は [Day 7](PRODUCT_API.md) で実装・試験し、売上の期間横断部分はDay 9に行う。

### 整合性と性能の範囲

単一Queryの強い整合性は、複数日・複数ページを一つのスナップショットにする機能ではない。**同時更新がない同じデータ状態**で、画面・集計・CSVが一致することを初期保証とする。ページ間の同時更新、日付訂正中の読み取り、過去時点の帳票再現は別問題として残す。

100売上/日、366日なら最大36,600売上を読み得る。現段階で応答時間・RCU・Lambda上限への適合は保証しない。Day 15で事前集計の採否、Day 17でCSVジョブ、Day 20で性能と上限を評価する。集計が処理予算を超えた場合は503 `QUERY_BUDGET_EXCEEDED`とし、途中合計を正常結果として返さない。Scanへの自動切り替えはしない。

## 4. トランザクションと競合

| 書き込み | 同時に確定する項目 | 最大アクション数 |
| --- | --- | --- |
| 商品登録 | 商品・コード予約・冪等性記録 | 3 |
| 商品更新 | 旧版条件付き商品・冪等性記録 | 2 |
| 売上登録 | 最新版・版1履歴・日付別参照・冪等性記録・商品条件確認 | 4＋異なる商品数、最大54 |
| 同日訂正 | 旧版条件付き最新版・新履歴・同日参照・冪等性記録・必要な商品条件確認 | 最大54 |
| 別日訂正 | 旧版条件付き最新版・新履歴・旧日参照削除・新日参照追加・冪等性記録・商品条件確認 | 最大55 |
| 取消 | 旧版条件付き最新版・新履歴・同日参照・冪等性記録 | 4 |
| CSV受付（予定） | ジョブ・冪等性記録 | 2 |

商品条件確認は、新規明細・商品差し替え・明示的なスナップショット再取得で、読み取った商品版と有効状態が保たれているか確認する。同一商品へのConditionCheckは重複させない。保持した旧明細の訂正・取消には、現在の商品が無効でもこの条件を課さない。

最新版と旧日付参照は読み取った版に一致する場合だけ変更する。新履歴・新日付参照・新要求キーは存在しない場合だけ追加する。同日参照はPutだけとし、同じ項目へDeleteとPutを重ねない。競合時は全体を失敗させ、部分保存を残さない。

AWSの上限は100の異なる項目、トランザクション全体4MiB、1項目400KiB。検証ツールでは余裕を持ち、型付きAttributeValueをASCII JSONにした大きさを**1項目256KiB、全体3MiB、55アクション以内**に制限する。これはAWSの厳密な項目サイズ計算ではなく保守的な設計ガードで、本実装時にも実際の全項目を検査する。[トランザクション仕様](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html)、[制限](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Constraints.html)

50商品・50明細・100文字の補助平面Unicode名称を使った例では、別日訂正が55アクション、最大項目153,333 bytes、要求JSON 400,589 bytesだった（テーブル名`fixture`の検証例）。MiniStackでも54/55アクションの登録・別日訂正を実行する。実AWSの限界値試験ではない。

## 5. 訂正・再送の扱い

訂正要求には既存明細の`line_id`を付けられる。同じ商品なら旧商品コード・名称を保持し、単価と数量は要求した整数値で更新する。無効商品の旧明細も保持できる。新規明細・商品変更では現在の有効商品からスナップショットを作る。既存明細の名称も更新したい場合は`refresh_product_snapshot=true`を明示し、有効商品の版を確認する。未知・重複する明細IDは拒否し、要求から外した旧明細は最新版から除く。履歴は残す。

要求キーは店舗・操作者内で一意。将来のHTTP実装ではmethod、正規化path、正規化JSON本文、If-Matchをハッシュに含める。認証・権限を確認した後、同じ要求なら保存した最初の成功応答を返す。別内容なら409。再送判定は現在版との比較より先に行い、登録後の訂正によって元の再送が失敗しないようにする。キーの同時作成が競合したら確定済み記録を再読込する。

SDKのClientRequestTokenだけに頼らず、冪等性記録を保存する。初期版で自動TTLは設定せず、保持期間・容量とプライバシーはDay 24で決める。記録の削除後まで永久に同じ再送を識別できるとは扱わない。
